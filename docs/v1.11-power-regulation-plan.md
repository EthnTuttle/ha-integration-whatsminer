# v1.11 power regulation: set.miner.power instead of restarts

Status: implemented behind the **Power Regulation** option (default `adjust_power_limit`, so the update changes nothing until it is switched on). Code: `api_v3.py` (`set_miner_power`, `get_miner_status`), `coordinator.py` (the `up_freq_finish` poll, `power_api`), `controller.py` (`_command_power`, `_regulation_tick`, the `V3_*` constants). Tests: `tests/test_power_regulation.py`.

---

## 1. The problem: every power change is a restart

Through 1.10 every power change went out as v2 `adjust_power_limit`. MicroBT documents that this restarts btminer, and so do v3 `set.miner.power_limit` and `set_target_freq` (MicroBT v2 API PDF V2.2.2; support article 423). Each restart costs:

- minutes of zero hashrate, then a fresh frequency tune of 15-20 min at reduced hashrate;
- an `Elapsed` reset, which the floor learner has to classify as ours or not;
- a boot hold (600 s) during which the controller cannot act except for safety;
- wear and risk. The M64 had hashboard faults (codes 560-563, then 2320) during the weeks of 20-40 restarts a day, and restart churn is the leading suspect.

1.8.2 (settled hold, predictive limiting) and 1.10.0 (daily strategy) cut the number of restarts. They did not remove the cost of each one.

## 2. The verified mechanism

v3 `set.miner.power` sets the **operating power** in watts. The API doc calls it "dynamic effective" once frequency tuning has finished. "If set during frequency tuning, effective next boot."

Live test on this miner, 2026-10-12 22:40 (M64_VL40, H616, firmware 20250409.15.REL, API 3.0.1). Full log with HA state snapshots before and after: `/home/ethan/network/power-test-20261012-220429.log`. Client: `/home/ethan/network/set_miner_power.py`.

- Wire format: `{"cmd":"set.miner.power","param":1250,"token":…,"account":"super","ts":…}`. `param` is a JSON **number**. The token is `base64(sha256(cmd + super_password + salt + ts))[:8]`, the same as `set.miner.service`. The default super password `super` was accepted.
- The miner answered code 0, `msg "ok"`.
- Power ramped 1884 → 1472 → 1242 W within about 30 s and held about 1240 W. Frequency fell 242 → 152 MHz. Hashrate tracked: 90 → 73 → 61 → 55 → 50 TH, about 85 % of the pre-step TH/W through the ramp.
- `elapsed` kept counting (33 → 97 s). **No restart.**
- `up-freq-finish` was 1 before the write and 0 at the next sample (16 s later). It stayed 0 for the rest of the watch: the power change starts a real re-tune.

The restart at T+80 s was not the command. The miner had restarted on its own 34 s before the write and came back reporting a derated limit of 1905 W. The 1.10 floor enforcement read that as "believed limit 1905 W < learned floor 1950 W" and sent `adjust_power_limit(1950)`. The telemetry limit flipped to exactly 1950 at the next poll, and the restart followed. After that, `get.miner.setting` showed no power override. The tune chased the 1950 W limit.

Facts the design takes as requirements:

1. `adjust_power_limit` **supersedes** the `set.miner.power` record. After one, the operating power is the limit again.
2. On API 3.0.1 `set.miner.power` is **not persisted** across btminer restarts. 3.0.3+ records it in the user config. A firmware upgrade is planned. The 2026-10-13 attempt did not apply (`/home/ethan/network/firmware-upgrade-20261013-072255.log`).
3. A **transient telemetry limit** below the floor must never be acted on as if it were the limit in force.
4. A power change starts a **re-tune** (`up-freq-finish` 0 for 15-20 min). No further step should be sent until it finishes.
5. During tuning, `set.miner.power` does nothing until the next boot. The **limit is the only lever during a boot**.
6. The miner held 1899 W (`power_floor_proven_ok`) and failed to hold 1700 W (`power_floor_unholdable_limit`). Regulation must not go below the evidence.

## 3. Design

### 3.1 The limit becomes a ceiling at Power Max

`set.miner.power` moves the operating power *under* the limit. The limit is the ceiling, so the ceiling has to sit at `Power Max` for regulation to cover the whole range. Raising it is one `adjust_power_limit`, which means one restart. After a restart (on API 3.0.1) the miner tunes toward the ceiling until the operating power is re-sent (fact 5). So the moment the ceiling goes up is chosen on purpose:

- **Lazily.** The ceiling is not raised the moment the option is turned on. It goes up the first time the regulator asks for **more than the limit in force**. That is exactly when the legacy path would have spent a restart anyway. Below the current limit, `set.miner.power` already covers everything, so turning the option on costs no restart until more power is needed.
- **Only when the loop can take a boot at Power Max** (`_ceiling_ok`): no cap engaged, supply not hot (within 5°F of the cap, or within the hot window), a zone calling and no shutoff dwell (a stagnant loop has no flow to carry 3.5 kW away), soft start finished (the soft start exists to keep resumes from overshooting), `set.miner.power` not in a rejection back-off, and the ceiling not held down after a tuning timeout. A safety clamp or floor enforcement that lands above a lower clamp in force never raises it either.
- **Otherwise the increase goes out as `adjust_power_limit(new_power)`**, which is exactly the 1.10 behaviour. A refused ceiling is never worse than today.
- **When Power Max is lowered**, a ceiling above it is lowered once, while the miner is tuned and outside a boot hold. Left alone, every later boot would tune above the new Power Max.

The ceiling (`_limit_w`, the last limit sent) is persisted (`power_limit_w`). The telemetry limit only replaces it after `LIMIT_PERSIST_POLLS` (3) polls that disagree, with btminer up for `BOOT_TRANSIENT_S` (120 s) and no command of ours in flight (see 3.5).

### 3.2 Regulation through set.miner.power, gated on up-freq-finish

Every power decision goes through `_command_power`. That includes the PID output, the demand-lockout and dwell clamps, the supply and chip caps (and the freeze-guard hold over the lockout) while hashing, the probe-loss fallback curve, the daily plan and floor enforcement. Their gates (step bands, intervals, boot hold, predictive rules) are unchanged. In order:

1. Above the limit in force: ceiling or legacy increase (3.1).
2. `set.miner.power` in its rejection back-off: `adjust_power_limit`.
3. Not tuned (3.3): safety clamps use the limit, and everything else is held.
4. Tuned: `set.miner.power`.

**Tuned** means a fresh poll, `up-freq-finish == 1`, and at least `V3_TUNE_GRACE_S` (90 s) since our own write. Live, the drop to 0 showed 16 s after the write, but at a 30 s scan interval the first poll can still carry the old 1. Because of this gate, no further step is sent while a re-tune runs (fact 4). The existing intervals still apply on top.

`up-freq-finish` comes from v3 `get.miner.status` `summary`, one unauthenticated read per poll, made after the v2 batch like `status` (the firmware caps concurrent connections). The read runs only with the option on, so the default polls exactly as before. A failed read is `None`, which counts as **not tuned**, never as tuned.

A held change only moves `_op_target`. `_last_commanded_power` stays what was actually delivered, so a later safety clamp to the same value still fires (`test_a_held_target_does_not_suppress_a_safety_clamp_to_the_same_power`). A `set.miner.power` is not a restart, so it does not mark an actuation. A restart that follows one is the miner's own, and it is floor evidence at that power.

### 3.3 The boot window

While the miner is tuning (after a start, a restart or our own write), `set.miner.power` would only apply at the next boot. Policy:

- **Safety keeps the limit.** The supply and chip caps (and the freeze-guard hold over the lockout) and the predictive back-off clamp with `adjust_power_limit`, as in 1.10. This costs a restart, but it is the only lever that acts now, and their authority is unchanged. Once tuned, the same clamps go out as `set.miner.power`.
- **Everything else is held.** That covers PID steps, the demand-lockout clamp, the daily plan and floor enforcement. Each is recorded as the target and sent once tuning finishes. Floor enforcement waits on purpose: answering a sub-floor reading with the limit during a boot is exactly the 2026-10-12 stomp.
- **The ceiling consequence.** After a reboot on API 3.0.1 the miner tunes toward the ceiling (`Power Max`) until the target is re-sent. Three things bound that window:
  - the boot hold, which blocks non-safety changes;
  - the caps and the predictive back-off, which use the limit clamp during tuning;
  - `V3_TUNE_TIMEOUT_S` (45 min): if the miner is still not tuned and runs above the power we want, the wanted power is sent as the limit and the ceiling is held down for 6 h. This one-shot condition stops a miner that never finishes tuning (2026-10-13 07:22: `up-freq-finish` 0 after 636 s, 15 TH at 1546 W) from sitting at 3.5 kW.

  Lowering `Power Max` shrinks the burst if it proves too large.

### 3.4 Re-established after every start

Every mining start edge, confirmed `Elapsed` regression, HA restart and `adjust_power_limit` marks the regulation layer *not established*, and the operating power is believed to be the limit. Once tuned, `_regulation_tick` re-sends the target with one `set.miner.power`. On API 3.0.1 that restores what the restart discarded. On 3.0.3+ the value persisted, and re-sending it is harmless. Re-sending is right in both regimes (fact 2). Nothing is sent when the target is at or above the limit, or was already delivered since the restart. The target is persisted (`regulated_power_w`), so an HA restart re-establishes it and seeds the PID from it, not from the ceiling.

### 3.5 Fallback and reset

- If `set.miner.power` is rejected with a non-zero code after the -4 unlock and one retry, or if 4433 fails `V3_TRANSPORT_FAILS` (3) times in a row, that command goes out as `adjust_power_limit`. Then:
  - `set.miner.power` is skipped for `V3_POWER_RETRY_S` (30 min), and the next command after that tries it again;
  - one `power_fallback` notification is raised, and dismissed on the next v3 success;
  - `power_api` reads `v2_fallback`.
- **Reset semantics** (fact 1): after any `adjust_power_limit` under this option (fallback, boot-window clamp, ceiling, timeout, collapse undo, booting-floor enforcement), the operating power is the limit. The limit is recorded as the new `_limit_w`. If the wanted power is below the limit, it is re-sent once tuned (3.4). The next increase above a lower clamp raises the ceiling again (3.1).

### 3.6 Floor semantics

- **Evidence is the operating power.** The floor learner's run power (`_run_limit`) is `_op_in_force`: what we last delivered with `set.miner.power`, or the limit after any restart or `adjust_power_limit`. A crash after re-establishment counts at the regulated power (1700 W in `test_short_runs_are_floor_evidence_at_the_operating_power_not_the_ceiling`). A crash during a boot, before re-establishment, counts at the ceiling, and the ceiling is above anything the floor could reach, so it is reported as a restart loop and not learned. This is conservative: a ceiling-tune crash is never read as low-power evidence.
- **The hardware-fault distinction is kept.** A restart at a power held within 7 days is fault evidence, not floor evidence. A power counts as held only after it has been in force for `FLOOR_STABLE_S` (15 min). There is no restart to start the clock, so it starts at the write.
- **The floor bounds the regulation output.** `out_min_effective` is the floor, now applied to the operating power. Floor enforcement while hashing believes only the power we commanded, never a telemetry value. While booting it believes the limit we sent. If we never sent one, it uses the reported limit only after it has persisted for 3 polls and 120 s of uptime (`test_a_transient_derated_limit_does_not_trigger_floor_enforcement`, `test_unknown_limit_enforces_the_floor_on_a_booting_miner_only_once_it_persists`).
- **Not below the evidence** (fact 6). Regulation never goes below the learned floor (1950 W here), so it does not start below the proven 1899 W band. Nothing steps the floor down on its own. `Power Min` (1200 W) is never the regulation target: it remains only what an engaged cap clamps to, as since 1.8.1.
- **Hashrate collapse.** After a `set.miner.power` step between two regulated powers, hashrate per watt is watched for `V3_COLLAPSE_WATCH_S` (30 min). Below `V3_COLLAPSE_FRAC` (½) of the pre-step value for 3 polls in a row, the step is undone with `adjust_power_limit(max(before, after))`. For a reduction, the pre-step power becomes `regulation_min_w`, which raises the effective floor (persisted, cleared by **Reset Learned Floor**), and a `power_collapse` notification is raised. Hashrate per watt, not hashrate, is the measure, so a normal ramp (85 % live) passes. The miner's sick post-restart state (10-13 TH at 1100-1400 W against 48 TH/kW before) would not.

## 4. Rollout and rollback

**Rollout**

1. Deploy 1.11.0 with the default `adjust_power_limit`. Nothing changes: no v3 summary read, and the same commands at the same times. The 1.10 suite passes unchanged.
2. Configure → first step → **Power Regulation** `set_miner_power`. The entry reloads, and the controller re-sends the stored target once tuned (none on the first enable).
3. Watch the Control Mode sensor's `power_command_path`, `power_last_command`, `up_freq_finish`, `power_limit_ceiling` and `regulated_power`, and the Mining Status `power_api`. Expect one restart, when the ceiling first goes up. After that, PID steps should read `set.miner.power … (regulate, no restart)` in the log, with `Elapsed` counting through them.
4. Check for `power_fallback` and `power_collapse` notifications. Check that the restart count per day falls.

**Rollback**

Set Power Regulation back to `adjust_power_limit`. The summary read stops. The limit is still the old ceiling, and the miner runs at the regulated power, so on the first hashing tick outside a boot hold the last regulated power is sent once as the limit (one restart). After that everything is the 1.10 behaviour. Without this step, the next boot would tune toward `Power Max`.

## 5. Out of scope (open decisions)

- 20 vs 45 min supply dwell.
- Any automated retry of a 1250 W floor, and any automatic floor step-down.
- `set.miner.power_percent` (`{"percent", "mode": "normal"}`). The docs say it suits frequent changes, but it is not saved and is percentage-based. Kept as a documented alternative.
- HACS deployment and live testing.

## 6. Open risks for review

- **The boot burst at the ceiling** is inherent on API 3.0.1. Its size depends on how fast the dry cooler absorbs it. The caps, the back-off and the 45 min timeout bound it, but none of that has been run live.
- **3.0.3+ persistence.** If an operating power persists across reboots and the miner then crash-loops before it is tuned, crashes are attributed to the ceiling, so the floor learner does not see them. The legacy booting-floor enforcement and the restart-loop notification remain.
- **Telemetry during a v3 step.** The v2 summary `Power Limit` is assumed to keep reporting the limit, not the operating power, after `set.miner.power`. The live log's v3 `power-limit` stayed at the limit, which supports this, but the v2 field was not captured. As a guard, a reported limit equal to the regulated power is never adopted as the new limit.
